# Lab operator runbook — proposed, Kubernetes execution NOT RUN

This is a reviewed-input/manual-replacement proposal, not a proven rolling
upgrade or recovery procedure. Do not deploy until Owner binds the two actual
Workers, dedicated authorized namespace, image digest and CNI/admission setup.
The documentation example uses fake names and a non-existent image digest.

Prerequisites: IPv4 Calico primary attachment with
`container_settings.allow_ip_forwarding:false`; approved Multus/NAD CRD,
VLAN/static IPAM binaries, trunk NIC and external VLANs; exact hostname selectors
matching one distinct Worker each; pre-existing lab admission for the explicit
lab-sysadmin profile. The Chart does not create namespace/admission exemptions,
RBAC, CNI installations or sysctl policy. Baseline/Restricted PSA will reject
the capability profile. Never alter cluster-wide policy to make this runbook pass.

## Initial install (proposal only)

Review the private lab values and pinned image; render/lint offline first.
Compare each of the eight NADs, two ConfigMaps and two Pods against the private
binding. Verify Calico IPv4 and all secondary plugin ordering; none may re-enable
forwarding. Install one approved release only after external prerequisites are
confirmed. The entrypoint checks final namespace forwarding, expected VLAN
interfaces and addresses before starting FRR. Any refusal is a failed start,
not authority to remount proc or change kubelet settings.

## One-sided desired snapshot replacement (proposal only)

Keep the old values, rendered manifests and immutable image identity for rollback.
Render a new reviewed desired release without applying it. Verify the *other*
RR is healthy and has the required client state before replacing one RR.

Stop/delete only the selected old Pod, wait for its actual termination, and
verify external CNI cleanup and release of the old VLAN attachments on its
bound Worker. An unreachable Worker or stale attachment blocks same-identity
activation; do not force-delete and guess, overlap incarnations or move it to
the other Worker. Apply only that RR's reviewed ConfigMap/NAD snapshot and then
its new bare Pod from the rendered release. Verify forwarding, boot-config
bytes, loopback, daemon state and actual routing acceptance before considering
the second RR. Keep Helm ownership metadata intact on resources generated by
the release. Reconcile the complete Helm release bookkeeping against the exact
reviewed final render only after validating this ordering in the lab.

This is deliberately **not a copy/paste helm upgrade command**: Helm's concrete
release-state/delete/recreate ordering and rollback must be validated in the
real lab. Helm does not continuously recreate missing bare Pods. ConfigMap or
checksum changes do not reload an existing FRR process. Do not use helm --force
or uninstall the whole release as a substitute for one-sided replacement.

Rollback means the same explicit single-RR replacement with the saved previous
values/image snapshot, after verifying cleanup and the surviving RR. Do not
claim rollback or interrupted-replacement support until observed. The original
Node must be restored before recovery from its failure; no automatic relocation.

## Diagnostics after separately authorized deployment

Read `/proc/sys/net/ipv4/ip_forward`, `/config/*` versus `/etc/frr/frr.conf`,
`ip -4 addr`, `ip -d link`, and `vtysh` outputs: `show running-config`,
`show ip ospf`, `show ip ospf neighbor`, `show ip route`,
`show bgp ipv4 unicast summary`, `show bgp ipv4 unicast`, and BGP next-hop state.
Inspect Multus attachment status and actual client NEXT_HOP/FIB/packet paths.
The readiness probe intentionally ignores remote neighbor availability.
Never publish private lab values or unredacted routing logs.
